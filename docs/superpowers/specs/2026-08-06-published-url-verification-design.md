# 发布 URL 校验增强设计

## 目标

增强 GitHub Pages 发布后的 URL 校验，使短暂的边缘节点传播延迟不会在一分钟内误判整次工作流失败，同时让永久性配置错误尽快失败，并在 Actions 日志中保留足够的诊断信息。

## 范围

本次只修改 `src/ai_news_sniffer/cli.py` 中的发布 URL 校验，以及 `tests/test_cli.py` 中的相关测试。工作流的 job 依赖、部署方式、运行状态写入和通知流程保持不变。

## 校验时限与重试

- 整个校验过程的墙钟时间预算为 8 分钟，包括 HTTP 请求耗时和重试等待。
- 首次请求立即执行。
- 暂时性失败后的等待秒数遵循斐波那契数列：`1, 1, 2, 3, 5, 8, 13, ...`。
- 每次请求和等待都受剩余预算限制；最后一次等待可以截断到剩余预算，不得故意让总过程超过 8 分钟。
- 成功取得 2xx 响应且页面包含 `AI 每日情报` 标记时立即返回。

## 错误分类

### 暂时性错误

以下情况在剩余预算内继续重试：

- HTTP 404；新日报路径可能尚未传播到所有 Pages/CDN 节点。
- HTTP 408、425、429。
- HTTP 500–599。
- `httpx` 网络传输错误和超时。
- HTTP 2xx，但页面暂未包含预期标记；这可能是边缘节点仍在提供旧内容。

预算耗尽后，抛出 `RuntimeError`。最终错误信息包含最后一次状态码或异常类型，以及最后一次实际 URL。

### 永久性错误

以下情况不重试，立即抛出 `RuntimeError`：

- URL 无法解析，缺少主机名，或协议不是 HTTP/HTTPS。
- 除暂时性状态之外的 HTTP 4xx，例如 400、401、403、405、410、422。
- 无法正常完成的重定向或其他非 2xx/非暂时性 HTTP 状态。

永久性错误信息明确标记为配置错误，并包含状态码、请求 URL 和最终 URL（若响应存在）。

## 日志

每次请求都向 stderr 输出一条结构化、便于 GitHub Actions 搜索的日志，至少包含：

- 当前尝试次数。
- 请求 URL。
- 实际最终 URL；没有响应时记录为不可用。
- HTTP 状态码；网络异常时记录异常类型。
- 分类结果：`success`、`transient` 或 `permanent`。
- 暂时性失败时的下一次等待秒数和剩余总预算。

日志不得只保留 `HTTPStatusError` 类型而丢弃实际状态码。

## 可测试性

校验函数允许测试注入单调时钟和 sleep 函数，生产环境默认使用 `time.monotonic` 与 `time.sleep`。测试使用受控假时钟，不产生真实等待。

测试覆盖：

- 首次成功并记录状态码与最终 URL。
- 404 后按斐波那契间隔重试并最终成功。
- 持续 5xx 时在 8 分钟预算耗尽后失败。
- 403 等永久性 4xx 立即失败且不 sleep。
- 非 HTTP(S) 或缺少主机名的 URL 立即失败。
- 2xx 旧页面缺少标记时作为暂时性问题重试。
- 网络错误作为暂时性问题重试。

## 非目标

- 不改变 `PUBLIC_BASE_URL` 的配置来源。
- 不改用 GitHub Pages deployment 输出 URL。
- 不自动重跑、补发通知或修复今天已停留在 prepared 状态的运行记录。
- 不引入新的第三方依赖。
